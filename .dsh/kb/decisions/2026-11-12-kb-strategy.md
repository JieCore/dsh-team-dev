## 背景

团队模式有三个痛点：新会话失忆、单会话过长触及上下文上限、跨团队知识不共享。
曾提出两个方案：把 `dsh-team-dev` 改为 Agent 预设模式（新增会话默认用该预设）；以及在插件内自建知识库工具。

## 决策

1. **不改成 Agent 预设模式**：`dsh-team-dev` 是 bundle，已对所有会话默认生效，便捷性并非其短板；预设化会引入 `standard` 副本漂移、副本无升级通道、broken 预设导致会话无法创建，且"设为默认"等价于退回全局。
2. **共享记忆用 0 代码方案**：根 `AGENTS.md`（≤2KB，常驻）+ 嵌套 `AGENTS.md`（懒加载）+ `.dsh/kb/`（0 固定成本）+ 现成 `grep`/`read` 检索 + `session_search` 跨会话检索。
3. **拉取式，不注入**：KB 不进系统提示，不自动加载；agent 判断需要时才 `grep`/`read`。`index.md` 全量读入是禁止动作（100 页≈3K token，300 页≈10K，线性增长）。
4. **写入只在显式收尾**：`team-guidelines.md §A`；不自动 ingest、不在会话开始时编译。
5. **单会话过长不靠 KB**：靠 `compaction`；KB 只承担跨会话记忆。两者是不同机制，别混用。

## 备选与为什么没选

| 备选 | 否决理由 |
|---|---|
| 预设化 + 新会话默认预设 | 默认即全局，白付预设化成本；`standard` 漂移与无升级通道是结构性问题 |
| 插件内建 `kb_search`/`kb_brief` 等工具 | 现成插件已覆盖读路径；等实测数据证明不足再加，避免先造工具后找场景 |
| `mcp-client` 接 Obsidian / Memory MCP | 每个 MCP 工具定义都进每次请求，token 成本高且引入外部进程；先不启用 |
| 向量库 / embedding | 空间级知识库规模（百页级）用 grep + 索引足够；引入后反而增加维护面 |

## 后果（含风险与缓解）

- ✅ 固定 token 增量 ≈ 0；根 `AGENTS.md` 压缩本身即是一笔节省（原预算 65536 字节）
- ⚠️ **KB 错误会扩散**：错误知识被所有后续会话继承。缓解：KB 一律视为 L2 证据，引用前回源码抽查；决策页必须带 `文件:行号`；`status: superseded` 保留旧结论不删除
- ⚠️ grep 无相关性排序：页面 > 200 后命中率可能下降。缓解：`index.md` 作导航；到瓶颈再评估检索工具
- ⚠️ 无结构校验（frontmatter / 死链）：靠收尾规则 + 定期人工 lint

## 何时重新评估

满足任一条件再考虑写工具（写进插件）：
1. 两周后跨会话返工率未下降；
2. KB 页 > 200 且 agent 检索命中率明显不足；
3. 多会话并发写同一空间 KB 出现真实冲突；
4. 需要"每次请求都生效"的写入拦截（工具级校验），才值得做成插件能力。
