# 内置开发准则（Team Dev Guidelines）

> 随 `team-dev` 技能发布（rank 600）。**所有成员开工前必读**；Lead 在阶段 0 读取本文件并把路径写进任务卡「输入材料」，任务卡「适用准则条款」引用本文件条款编号。
> 目标：让「什么算做对」在开团前就有统一、可执行的答案，而不是等到评审时各说各话。

## 1. 生效方式与项目级覆盖

### 1.1 优先级（冲突时从高到低）

| 层级 | 来源 | 说明 |
|---|---|---|
| **项目级（最高）** | 项目根 `AGENTS.md`、`CLAUDE.md`、`.dsh/team-guidelines.md` | 存在即生效；同名条款覆盖内置 |
| 用户级 skill | 用户目录下的 team-dev 技能资源（rank 400） | 覆盖随包技能 |
| 内置（本文件） | `skills/team-dev/guidelines.md`（rank 600，随包） | 项目级未覆盖处的默认 |

- 三个项目级文件可同时存在：按 `AGENTS.md` → `CLAUDE.md` → `.dsh/team-guidelines.md` 顺序读取；三者冲突时以 `.dsh/team-guidelines.md`（团队级、最具体）为准。
- **覆盖语义**：同名条款项目级优先；项目级未涉及的条款回退本文件；项目级只能追加更严要求，**不得放宽「§4 数据与安全」与「§7 质量门」底线**。确需放宽时由 Lead 裁决，并写进交付报告。
- 项目级文件属于共享文件：只有 Lead（或项目 owner）能改，成员不得在任务里顺手修改。

### 1.2 Lead 开工前（阶段 0 必做）

1. 读项目根三个准则文件（存在即读），记录与本次改动相关的条款。
2. 读本文件。
3. 任务卡「输入材料」写：`skills/team-dev/guidelines.md` + 项目级文件实际路径；没有项目级文件时写明「项目级准则：无」。
4. 任务卡「适用准则条款」填写适用条款编号，例：`guidelines.md §5.2 前端列表排序规范`。
5. 项目级要求与任务卡冲突时，Lead 先裁决并改任务卡，不把冲突留给成员。

### 1.3 成员开工前（任务执行第一步）

- 读任务卡「输入材料」列出的内置准则与项目级准则。
- 发现任务卡要求与准则冲突（例：要求改共享文件、要求跳过测试、要求跨团队操作）：**停下报告 Lead**，不得按冲突要求实现，也不得静默按准则改需求。
- 自检时对照「适用准则条款」逐条勾选，未覆盖项说明原因。

### 1.4 写项目级准则的建议

- Markdown 格式，条款标题与编号自定；建议用 `[覆盖]` / `[追加]` 标明与内置条款的关系。
- 只写「本项目特有」内容：命令、目录、命名、接口风格、领域约束；通用内容直接引用本文件，不要复制。
- 新成员靠这份文件就能知道项目的硬规则；写完由 Lead 在任务卡引用。

## 2. 通用工程准则

1. **最小改动**：只改任务卡写作用域内的文件；不重构、不格式化无关代码、不顺手升级依赖。
2. **先读后写**：改文件前先读；已有实现优先于新写法；写之前说明改哪里、为什么。
3. **失败要大声**：异常不吞、降级要显式（返回降级状态/文案），不允许静默返回空。
4. **可验收**：每个任务卡有可执行验收命令与期望输出；「应该可以」不是证据。
5. **边界先于功能**：空值、空集合、超长输入、并发/重复操作、失败路径先想清楚。
6. **提交与回滚边界**：Git 写操作只有 Lead；成员产出以新增/最小改动为主，便于回滚。
7. **假设显式化**：不确定写「待确认」或 `team-out/assumptions.md`；影响正确性的假设升级 Lead。
8. **粒度**：单任务 ≤ 3 文件、≤ 200 行；超出拆任务或串行。
9. **唯一 owner**：每个文件只有一个 owner；写作用域文件级零重叠；共享文件由 Lead 独占。

## 3. 前后端契约

1. **接口先定**：请求/响应字段、类型、错误码、空值语义、排序/分页参数先进 design 或任务卡，再写两端。
2. **三件套**：列表/详情页必须同时设计**加载态、空态、错误态**；错误可重试，空态有下一步指引。
3. **错误归一化**：网络错误、HTTP 4xx/5xx、业务错误统一成前端错误模型；错误文案不暴露内部细节。
4. **请求生命周期**：超时、取消（AbortController）、单在途请求；旧请求不得覆盖新状态。
5. **只读/写分离**：只读接口不产生副作用；写操作考虑幂等与失败回滚。
6. **前端边界**：宿主插件的客户端代码不跨插件值导入（只 type-import）；React 等由宿主共享；主题色用宿主 CSS 变量或继承色。
7. **契约变更**：字段改名/删除必须向后兼容（保留旧字段或默认值），并在任务卡说明；破坏性变更标 `[breaking]` 由 Lead 决策。
8. **展示与数据一致**：前端展示字段与后端返回同名同义；前端计算字段（计数、排序）注明来源。

## 4. 数据与安全

1. **只读数据不落盘**：看板/列表等只读数据不写 localStorage 或日志；仅无敏感 UI 偏好（选中 teamId 等）可本地记忆。
2. **日志脱敏**：不记录任务 subject/description、消息正文、token、密钥、PII；日志只记 id、数量级、错误类型。
3. **路由信任栅栏**：本机 HTTP 接口复用宿主 `connection` 鉴权；只暴露 GET；响应 `cache-control: no-store`；路径参数做格式校验。
4. **不代持权限**：前端/插件不缓存鉴权凭证，不绕过宿主服务直接读文件或数据库。
5. **敏感信息不进任务卡**：任务卡、看板、消息中出现敏感数据时脱敏，或改为引用文件路径。
6. **资源清理**：定时器、事件监听、请求、连接在卸载/切换时释放（`ctx.effect` cleanup / `useEffect` cleanup）。
7. **数据范围最小化**：接口只返回页面需要的字段；跨团队/跨租户数据默认不可见。

## 5. 排序与命名

### 5.1 排序与命名通用

- **稳定且确定**：任何列表输出（接口、看板、文档表格）必须有确定的顺序：**可交互排序**的列表按 §5.2 声明显式排序与 tie-breaker，禁止依赖查询/遍历的默认顺序；**只读展示**列表（如团队看板）以服务端契约顺序为准（团队列表由 host 按 teamId 稳定排序，任务/成员按 Agent Teams 服务返回的持久化顺序），客户端不得随机重排，并在组件注释里注明顺序来源。
- **命名一致**：同一概念前后端同名字段（`updatedAt` 不写成 `update_time`）；文件、任务、团队名唯一且可检索。
- **归属清晰**：一个文件一个 owner；归属表零重叠；命名体现职责（`*-board`、`*-api`），不留 `util2`、`temp`。

### 5.2 前端列表排序规范（可执行）

> 本节适用于**提供用户可操作排序**的前端列表；评审逐条核对，缺项按 `[blocking]` 处理。只读展示列表（团队看板、任务列表等）不提供排序控件，按 §5.1 的只读顺序约定处理，不适用本节。

1. **排序状态如何表达**
   - 单一状态：`sortBy: Array<{ key: string; direction: 'asc' | 'desc' }>`（单列也用长度为 1 的数组）；禁止用多个散落状态（`sortField` + `sortAsc` + `isDesc`）表达。
   - `key` 必须等于数据字段名（与后端契约同名），不得用展示文案、列下标或本地化 key；`direction` 只允许 `'asc' | 'desc'`。
   - 排序状态由列表容器持有并下传，子组件只渲染不持有排序状态；默认受控。
2. **默认排序**
   - 每个列表必须声明**显式默认排序**常量，不得依赖后端返回顺序或未指定比较器的 `Array.sort`。
   - 默认排序要有业务含义且带稳定 tie-breaker（例：`[{ key: 'updatedAt', direction: 'desc' }, { key: 'id', direction: 'asc' }]`）；没有时间字段时用主键升序。
   - 默认排序必须能被用户感知（列头高亮，或「默认：更新时间倒序」提示）。
3. **多列排序优先级**
   - 点击顺序即优先级：先点为主排序键，后点为次排序键；数组顺序与 UI 序号（1/2/3）一致。
   - 同一列重复点击切换 `asc/desc`；回到默认状态后第三次点击恢复默认（或明确移除该列）——两种行为选一种并在组件内统一，禁止同一列表混用。
   - 最多 3 个排序键；超出拒绝并提示，不得静默截断。
4. **URL / 持久化**
   - 排序状态可分享：能写 URL 的页面同步 query（如 `sort=updatedAt:desc,id:asc`），刷新、前进后退、分享链接后排序一致。
   - 侧栏/弹窗等无法写 URL 的场景：状态保存在容器内，关闭重开恢复；同一页面复用同一套解析/序列化函数。
   - 用户记忆只存 `sortBy`（localStorage），不存列表数据；恢复时校验 key 在白名单内、direction 合法，非法值回退默认排序。
   - 从 URL/记忆恢复后必须真正重排数据，或按新排序重新请求，不能只改箭头。
5. **空值排序**
   - 空值（`null` / `undefined` / 空字符串 / 无效日期）统一视为「无值」，**无论升序降序都排在最后**；用组件内常量声明该规则，并在文档引用。
   - 不得依赖 JS 隐式转换比较空值；先显式判断 `isNilOrEmpty(value)` 再比较。
   - 类型比较规则：数值按数值、日期按时间戳、字符串按 `Intl.Collator` / `localeCompare(项目 locale)`；混合类型先按契约归类，不得用 `a > b` 直接比较。
6. **稳定排序**
   - 每个比较器必须有 tie-breaker（通常 `id asc`），保证相同数据多次排序、刷新、跨端展示顺序一致。
   - 不依赖运行时 `sort` 的稳定性承诺；自定义比较器在 `compare(a, b) === 0` 时回退到 tie-breaker。
7. **与后端排序契约**
   - 数据量超过阈值（如 200 行）或分页列表必须**服务端排序**：请求带 `sort` 参数（字段名与前端 key 同名、方向枚举），响应返回实际生效的排序。
   - 前端只对「已全量加载的小列表」本地排序；后端分页时禁止对当前页排序后展示（与分页语义冲突）。
   - 前后端比较语义必须一致（空值位置、大小写、数字/字符串、locale）；契约写进接口文档，联调用同一组数据对照。
   - 排序变化触发新请求或重排，并取消在途旧请求，防止旧响应覆盖新排序。
8. **文案与交互一致性**
   - 同一概念全站一种说法（「升序/降序」或「↑/↓」选一套）；排序方向、默认值提示、空态文案与项目术语保持一致。
   - 表头整列可点、`aria-sort` 正确、键盘可操作；排序请求中保留旧数据 + 顶部 loading，不清空已有内容。
   - 空列表时排序控件可见但禁用，或给出空态文案；不得因排序失败隐藏错误。
   - 排序失败保留上次排序状态与数据，错误条明确「排序失败，已保留上次结果」。

## 6. 本仓库（dsh-team-dev）契约

- `src/` 是唯一源码；`lib/` 是构建产物，**禁止手改**（只由 `scripts/build*.mjs` 生成）。
- host 顶层 `inject` 保持 `['agents', 'skills']`；新增服务一律可选探测 + 降级，服务缺失时插件照常加载。
- 本机 HTTP 接口：只读 GET、`cache-control: no-store`、参数校验、缺服务时返回 `degraded` 状态；不写敏感日志、不落盘。
- 客户端半侧：产物必须 `window.__ModuleLoader__.load` 包装；external 仅 `react` / `react-dom`；不得跨插件值导入；bundle ≤ 1.5 MB。
- 技能资源为 Markdown：provider 只注册 `SKILL.md`，其它资源以相对路径引用；改技能不得破坏 frontmatter `name` / `description` 语义。
- 零运行时依赖；不新增依赖除非 Lead 决策。
- README 双语对应（`README.md` ↔ `README.zh.md`）；提交信息用 conventional commits；Git 写操作只有 Lead。

## 7. 质量门（三道质量门）

| 门 | 谁 | 通过条件 |
|---|---|---|
| G1 自检 | implementer | 改动在写作用域内、目标命令本地通过、无遗留调试代码、写明未验证项 |
| G2 独立复核 | reviewer + tester | review 的 `[blocking]` 清零；测试覆盖正常 / 边界 / 失败路径；上游引用已抽查 |
| G3 终验 | Lead | 亲自跑全量命令、diff 范围核对、DoD 逐条勾 |

- 无自检不得 `complete`；无独立复核不得交付；证据必须是命令输出或 `文件:行号`，不能是「应该可以」。
- 上游产物（简报 / 设计 / review / test-report）是 L2：引用关键结论前回溯源码（≥3 条）；冲突以 L1 为准，并报告 Lead。
