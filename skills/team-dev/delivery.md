# 交付质量门（准确交付）

## 1. DoD 三层

| 层级 | 通过标准 |
|---|---|
| 任务级 | 改动在写作用域内 + 目标命令通过 + 无遗留调试代码 + 写明未验证项 |
| 阶段级 | review 的 `[blocking]` 清零 + 测试覆盖正常/边界/失败路径 |
| 交付级 | 全量命令通过 + diff 范围一致 + 交付报告 + 回滚方式明确 |

Lead 批准缩小范围时，按**新 DoD** 验收；`handoff-<task-id>.md` 里的未完成项必须转为新任务，或显式记为遗留风险。

## 2. G1 自检（implementer，complete 前必做）

- [ ] `git status` 自查：只改了任务卡写作用域内的文件
- [ ] 目标命令已跑，并在回报里贴结果（不是"应该通过"）
- [ ] 边界已处理：空值、空集合、越界、超长输入
- [ ] 错误有明确信息，没有吞异常
- [ ] 无新增 `console.log` / 调试代码 / 未说明的 TODO
- [ ] 未验证项、假设项已写明

## 3. G2 独立复核（reviewer + tester）

### reviewer checklist

- [ ] 逻辑正确，覆盖任务描述里的行为
- [ ] 边界与失败路径
- [ ] 空值 / 类型 / 并发 / 幂等
- [ ] 错误处理与资源释放（连接、文件、定时器）
- [ ] 安全：注入、路径穿越、越权、敏感信息进日志
- [ ] 兼容：接口 / 字段 / 配置 / 协议变更是否向后兼容
- [ ] 性能：N+1、循环内 IO、无界增长
- [ ] 可观测性：关键路径有日志，错误信息可定位
- [ ] 与仓库既有约定一致
- [ ] 测试是否覆盖本次改动（缺失就报 Lead 或 tester，不自己写）
- [ ] 断言是否可能恒真 / 在旧实现下也能通过（假通过）
- [ ] 上游引用已抽查（≥3 条），冲突已标注

### tester checklist

- [ ] 正常路径
- [ ] 边界值
- [ ] 失败 / 异常路径
- [ ] 相关回归用例
- [ ] 命令与结果可复现
- [ ] 修复类任务必须有一条在**旧实现上会失败**的回归测试

## 4. G3 Lead 终验

- [ ] 亲自跑全量 build / test / lint / typecheck
- [ ] `git diff --stat` 与任务卡范围一致，无越界文件
- [ ] 任务板全部 `completed`（看状态，不看消息）
- [ ] review 的 `[blocking]` 清零
- [ ] 交付报告完成，回滚方式明确

## 5. 上游信息核查（辩证判断）

- 上游产物（简报 / 设计 / review / test-report）属于 **L2 待核信息**，不是事实。
- 引用上游关键结论前，抽样回溯 ≥3 条到原始代码 / 命令输出；未核实的不进入结论。
- 发现冲突：以 L1 原始来源为准，在交付物中写明冲突点（`文件:行号`），并报告 Lead。
- 不得静默绕过：默默改对会让同一条错误扩散到其他人的交付物。
- reviewer 抽查引用是否成立；Lead 终验核对已知错误是否已修订或标注。

## 6. 证据纪律

- 结论必须带 `文件:行号` 或命令输出。
- 每个交付项标注状态：**已验证 / 未验证 / 假设**。
- 禁止"应该可以""大概率没问题"；不确定就进待确认清单。

## 7. 假设与问题清单

- 成员遇到不确定：写入 `team-out/assumptions.md`，格式：`谁 | 位置 | 假设内容 | 影响 | 需要谁确认`。
- 影响正确性的假设**必须**升级 Lead 决策，不得自行假设后 complete。

## 8. 常见失败模式（交付前逐条自查）

| 失败模式 | 典型表现 |
|---|---|
| 静默失败 | 异常被吞、返回空但不报错 |
| 边界泄漏 | 空值 / 空集合 / 超长输入未处理 |
| 范围越界 | 顺手改了无关文件或格式 |
| 只测 happy path | 无边界与失败用例 |
| 破坏兼容 | 改接口/字段名无迁移或默认值 |
| 不可回滚 | 数据迁移没有反向脚本 |
| 并发问题 | 共享状态无锁、非幂等 |
| 敏感信息 | 日志或错误信息带密钥、PII |
| 资源泄漏 | 连接 / 文件 / 定时器未释放 |
| 假完成 | 声称"已测试"但没有命令输出 |

## 9. 交付报告模板

```markdown
## 改了什么
- <文件>：<改动要点>

## 为什么
<关联任务、问题或需求>

## 怎么验证
- 命令：<命令> → 结果：<通过/失败数>
- 手工验证：<步骤与结果>

## 采用的上游结论
- <结论>（L2）→ 核实方式：<回溯的文件:行号 / 命令> → 结果：<成立 / 冲突>

## 风险与未覆盖
- 已验证：<...>
- 未验证：<...>
- 假设：<...>

## 回滚
<git revert / 配置回退 / 数据回滚步骤>
```

## 10. 优先级

正确性 > 兼容性 > 可维护性 > 性能 > 风格。
风格问题不得阻塞交付；正确性与安全问题必须阻塞。
