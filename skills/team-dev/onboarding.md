# 项目上手协议（Onboarding）

目标：≤10 分钟产出 `team-out/00-onboarding.md`，让全队具备"能改对"的上下文。**这是快速上手与准确交付的共同前提。**

## 1. 读取顺序（按性价比，不要通读）

| 顺序 | 读什么 | 为了得到 |
|---|---|---|
| 1 | `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md` / `README` | 硬性规则、禁止事项、提交要求 |
| 2 | 包与构建清单：`package.json` / `pom.xml` / `build.gradle` / `pyproject.toml` / `go.mod` | 技术栈、依赖、脚本命令 |
| 3 | 目录结构（限 2–3 层） | 3–6 个核心模块与边界 |
| 4 | 每个核心模块的入口文件各 1 个 | 调用链、分层方式 |
| 5 | 测试目录 | 框架、命令、覆盖薄弱区 |
| 6 | `git log --since="30 days" --name-only` 统计高频文件 | 变更热区与真正活跃的代码 |
| 7 | `grep TODO/FIXME` 集中区 | 已知坑 |

## 2. 纪律（违反会让简报变慢且不可信）

- **工具调用 ≤ 15 次**；先用 glob/grep 定位，再精读目标文件。
- 不读全仓、不逐行读超过 500 行的文件；大文件只读关键段落。
- 每条结论必须带路径（`文件:行号` 或命令输出）；查不到写「待确认」，不要猜。
- 简报写给**不了解这个项目的人**看：假设读者只有这份文档。
- 耗时超过 10 分钟要停下来，先交付当前版本并列出待确认项。

## 3. 输出模板 `team-out/00-onboarding.md`

每条结论后标注置信度：`[已验证]`（附 `文件:行号` 或命令输出）/ `[推断]` / `[待确认]`。

```markdown
# 项目简报：<项目名>
## 1. 一句话定位与技术栈
<这个项目是什么；语言/框架/包管理器/运行时版本>
## 2. 运行与命令
| 用途 | 命令 | 工作目录 |
| build | <命令> | <目录> |
| test | <命令> | <目录> |
| lint / typecheck | <命令> | <目录> |
## 3. 目录地图
| 模块 | 职责 | 入口文件 |
## 4. 关键入口
<启动流程、路由/命令注册、依赖注入、配置加载>
## 5. 代码约定
<命名、错误处理、日志、注释语言、提交信息规范>
## 6. 数据与外部依赖
<数据库、缓存、消息、第三方 API、环境变量清单（不含密钥值）>
## 7. 测试现状
<框架、命令、哪些区域有覆盖、哪些是空白>
## 8. 风险热区
| 文件/模块 | 风险原因 | 本次注意点 |
## 9. 本次改动落点
| 文件 | 拟改动内容 | 建议归属 |
## 10. 待确认清单
- [ ] <问题>（需要 Lead/用户决策）
```

## 4. 精简版（单模块小改）

只写第 1、2、8、9、10 节，其余一句话带过。

## 5. 交付检查

- [ ] 第 2 节的命令**实际执行过**至少一条，确认可用
- [ ] 第 9 节的落点文件**逐个打开确认存在**
- [ ] 第 10 节没有把"猜"写成结论
- [ ] 每条结论带置信度标注；`[已验证]` 的必须附证据
- [ ] 简报路径已写进每个成员任务卡的「输入材料」

## 6. 交给谁

- 简报由 Lead 或 `scout` 产出，放在 `team-out/00-onboarding.md`。
- architect 基于简报出 `design.md`；implementer / reviewer / tester 的任务卡「输入材料」必须包含简报路径。
- 简报不是最终方案：涉及架构取舍的交 architect/Lead 确认。

## 7. 使用约定（重要）

- 简报是 **L2 待核输入**，不是事实：成员引用其中结论时必须抽样回溯原始来源（≥3 条）。
- 发现简报与源码/材料冲突：以源码为准，在交付物里写明冲突点，并报告 Lead。
- 简报里的 `[推断]` / `[待确认]` 不得直接当实现依据；需要结论时先补验证。
