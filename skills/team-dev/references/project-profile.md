# 项目规则发现（阶段 0）

> 目标：在开团前回答「这个项目有哪些硬规则、收尾要求、命令和文件边界」，并把答案写进 `team-out/00-onboarding.md`。**只读与本次改动相关的条款，不要把整个 KB 搬进上下文。**

## 1. 发现顺序

1. 项目根 `AGENTS.md`
2. 项目根 `CLAUDE.md`
3. `.dsh/team-guidelines.md`
4. 上述文件里明确指向的规则文件（只跟一层）：如 `.dsh/kb/context/工作约定.md`、`构建约定.md`、`.dsh/kb/index.md`
5. 构建/测试入口：`package.json` scripts、`Makefile`、`justfile`、CI 配置

没有某文件就记「无」，不要猜。

## 2. 每条规则记什么

| 字段 | 例子 |
|---|---|
| 路径 | `.dsh/team-guidelines.md` |
| 作用域 | 全项目 / 前端 / 后端 / 交付 |
| 与 L0 关系 | 追加 / 覆盖 L1 / 冲突（停下报告） |
| 本次相关条款 | §A 收尾、§3.2 五项验证 |
| 证据 | `文件:行号` |

## 3. 项目 §A / 收尾要求

- 找到项目的「完成定义」：KB 沉淀、交付说明、验证清单、发布步骤。
- 记录成 checklist，阶段 5 **先做项目 §A，再做 L0 交付判定**。
- 项目 §A 不能替代 L0；项目要求「不要 present / 不要声明」时，按 L0 拒绝并报告 Lead。

## 4. 文件边界

- 共享文件：根 `package.json`、锁文件、路由入口、CI、迁移脚本、`AGENTS.md` / `README`。
- 多会话/多 worktree：记录本会话允许写的顶层目录；成员只写任务卡范围。
- 发现别的会话的改动出现在自己目录（或反之）：停下报告，不覆盖、不回滚。

## 5. 输出模板（写进简报）

```markdown
## 项目规则
- 规则文件：<path>（作用域：...；与 L0：追加/覆盖 L1）
- 本次相关条款：<§x ...>（证据：<file:line>）
- 项目 §A 收尾：<checklist>
- 构建/测试命令：<命令>
- 共享文件：<清单>
- 多会话边界：<允许写的顶层目录 / worktree>
- 缺失/冲突：<无 / 待 Lead 裁决>
```

## 6. 约束

- 项目规则文件是共享文件：只有 Lead/owner 能改，成员不得顺手修改。
- 项目规则可覆盖内置 L1 默认，**不能覆盖 L0**；冲突升级 Lead，写进交付报告。
- 只读相关条款；不要为了「完整」把 KB 全读一遍。
