# Team Dev — 专业化开发团队

```text
快速建团  →  角色目录 + 阵型 + 一次建完          → roster.md
快速上手  →  项目简报 00-onboarding.md + 侦察纪律 → onboarding.md
开发准则  →  通用/前端/本仓库契约 + 项目级覆盖    → guidelines.md
准确交付  →  三道质量门 + 证据纪律 + 交付报告     → delivery.md
```

三条原则：**Lead 切分与裁决、成员按文件归属执行、任务板是唯一状态源。**

**准则先于实现**：开工前读 `guidelines.md`（项目级 `AGENTS.md` / `CLAUDE.md` / `.dsh/team-guidelines.md` 优先覆盖），任务卡的「适用准则条款」就是验收依据。准则与项目级文件冲突时，项目级优先；不得放宽数据安全与质量门底线。

## 多对话 / 多团队（v0.2）

- **一个会话 = 一个团队**：TeamId 就是 root session id，每个 Lead 会话有自己的隐式团队、成员和任务板；多对话并发 = 多团队并存，天然隔离。
- 每团队一个 Lead（root session）；teammate 只属于创建它的团队，不跨团队复用、不跨团队派活，成员之间不直接通信。
- 跨团队协作只发生在 **Lead 与 Lead 之间**（各自会话内推进），不经任务板：不建跨团队任务、不共享任务卡/写作用域、不代其它团队 `complete`。
- Lead 只操作自己团队的任务板：`team_task_list` / `team_task_update` 的 task id、成员名单、看板当前团队三者必须一致；不确定先核对再动作。
- 任务卡「任务 id：<Lead 记录并告知成员>」中的 id 属于本团队；成员发现任务来自其它团队或指向其它团队资源时，停下报告 Lead。
- 团队 per-session：`inactive` 成员用 `send_message` 唤醒，不重建；会话（团队）结束后任务板作为记录保留，不与新会话共享。

## 团队看板（v0.2）

- **位置**：会话右侧栏的「团队看板」页签（`sidebar.right.pane.tab`，session scope，随当前会话展示）；默认选中当前会话所属团队。
- **刷新**：页面可见时每 **5 秒** 自动轮询；切到后台标签页自动暂停，回到前台立即刷新；顶部有手动刷新按钮和最后更新时间；连续失败按 5s → 15s → 30s 退避。
- **团队切换**：看板顶部下拉列出本机在线团队（Lead 名 + teamId 前 8 位 + 成员/任务数）；切换后只请求并渲染选中的那一个团队。
- **只读边界**：看板不提供创建 / 领取 / 完成 / 改依赖等写操作；所有状态变更仍走 Agent Teams 任务工具，看板展示以任务板为准。
- **Lead 巡检用法**：三列（pending / in_progress / completed）看阻塞（`blockedBy`）与写作用域告警（`writeScopeWarnings`）；发现异常仍用任务板工具和 `send_message` 处理，不在看板操作。
- **降级**：部署未启用 Agent Teams 时显示「此部署未启用 Agent Teams」；无团队时提示用 team-dev / team-boot 开团；看板异常不影响会话与任务板操作。
- 成员不需要也不应该操作看板 UI——看板是给 Lead / 用户看的观察面；团队成员之间的状态同步仍以任务板与 Lead 消息为准。

## 阶段 0：判断与上手（开团前，Lead 完成）

### 0.1 开团判据

| 条件 | 结论 |
|---|---|
| 改动 < 3 文件、< 200 行、无接口/依赖变化 | 不开团，Lead 直接做 |
| 无法切成文件级互不重叠 | 不开团，或改串行 |
| 缺可执行的验收命令（build/test/lint） | 先补命令，再开团 |
| 需要装依赖、改锁文件、跑数据迁移 | 这段 Lead 自己做，不派给成员 |
| 多模块、可并行、有验收命令 | 开团 |

### 0.2 项目上手（决定成员能不能一次做对）

- **陌生仓库 / 跨模块 / 改动 > 3 文件**：先产出 `team-out/00-onboarding.md`，目标 ≤10 分钟，模板与方法见 `onboarding.md`。
- **单模块小改**：产出精简版（技术栈、命令、风险热区、落点文件）。
- 简报完成后作为**所有成员任务卡的输入材料**，禁止每个成员重复摸索。
- 简报里的设计判断交给 architect/Lead 确认，不要当事实直接实现。

### 0.3 侦察与边界

1. 读 `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md` / `README`，记录格式化、提交、测试要求。
2. 确认真实命令：build / test / lint / typecheck，写进任务卡，不让成员猜。
3. `git status` + 当前分支 + 未提交改动；记下脏文件，验收时区分。
4. 列共享文件清单（见 `roster.md`），这些不分配给成员。
5. 按文件级切分，每块能独立验收。

### 0.4 读取开发准则（开团前必做）

1. 读项目根 `AGENTS.md` / `CLAUDE.md` / `.dsh/team-guidelines.md`（存在即读），记录与本次改动相关的条款。
2. 读本技能目录的内置 `guidelines.md`；项目级条款与内置冲突时**项目级优先**，项目级未覆盖处回退内置。
3. 任务卡「输入材料」必含：`skills/team-dev/guidelines.md` + 项目级准则文件实际路径；没有项目级文件时写明「项目级准则：无」。
4. 任务卡「适用准则条款」填写条款编号（例：`guidelines.md §5.2 前端列表排序规范`），成员按此自检、reviewer 按此复核。
5. 项目级要求与任务卡冲突时 Lead 先裁决并改任务卡；成员遇到未裁决的冲突必须停下报告（见 `roster.md`）。

## 阶段 1：快速编队（成员不固定，按需最小化）

角色目录是**能力清单，不是固定编制**；每场任务重新选人，成员实例 per-session 新建、不跨会话复用。阵型只是参考模板，不是必选套餐。

**最小可行团队**：从 1 人（Lead 自己做）开始，每加一人必须能回答「没有他，哪件事做不成或做不对」。

| 需求信号 | 加谁 |
|---|---|
| 改动有正确性/安全风险，需要独立评审 | + reviewer |
| 有测试基础设施，需要独立行为验证 | + tester |
| ≥2 个互不重叠文件块，可并行 | + implementer（第二个） |
| 方案/接口不确定，需先定归属 | + architect |
| 陌生仓库，Lead 没时间摸清 | + scout |
| 专项风险（安全 / 迁移 / 性能） | + specialist |

规模参考：小改 1–2 人；常规 2–3 人；攻坚 3–5 人；上限 8（含失败的）。
反例：任务本身串行、文件无法切分、一条命令就能验收时，加人只增加协调与 token 成本，不提升质量。
代码任务的**可并行度天然低于研究型任务**（依赖多、共享上下文多），优先少而精，不要照搬研究型团队的并行度。

**建队方式**：
- 并行任务：一次建完所有成员；创建期禁止 `wait_agent`，不要等任何人完成（单次 spawn 通常 < 1 秒）。
- 流水线任务：可以分批建——当前阶段成员先建，阶段切换时再建下一批；**建队动作不得和等待混在一起**。提前创建的下游成员以「待命」方式创建（`ready=false` 回报待命并结束本轮，由 Lead 唤醒）。
- 创建后 `list_agents` 核对 1 + N 行、无 `failed`，把原文回报用户。
- 角色目录、边界、prompt 见 `roster.md`。

## 阶段 2：任务下发（任务卡是唯一需求来源）

- 任务卡 9 项，缺一项不下发（模板见 `roster.md`）。
- 「输入材料」必含 `guidelines.md` 与（若存在的）项目级准则文件；「适用准则条款」按本次任务填写，不填视为任务卡不完整。
- **粒度**：单任务 ≤ 3 文件、≤ 200 行改动；超出拆给 implementer-2 或分阶段。
- **顺序**：先建 P1/P2 拿到 task id，再建 P3/P4（`blocked_by` 引用）。
- reviewer / tester 的 `blocked_by` 列全**所有**实现任务。
- 建完 `team_task_list` 自查：空描述、写作用域重叠、依赖指向错误。
- 工具语义：blocked 任务 `claim` 被拒；`complete` 要求 in_progress；`edit` 与 `set_dependencies` 是两次独立 CAS。
- **需求变更必须改任务描述**，不能只在消息里说；准则或范围变化时同步更新「适用准则条款」。

## 阶段 3：执行

- 文件归属同时写进 prompt 与 `write_scopes`；共享文件 Lead 独占。
- 成员开工第一步：读任务卡「输入材料」的准则与「适用准则条款」（见 `guidelines.md` §1.3）。
- 任务板是唯一状态源；消息只做「唤醒」和「异常」，成员之间不得直接通信。
- 上游 `completed` 后立刻 `send_message` 唤醒下游。
- 待命成员的 `inactive` ≠ 完成，别误判交付。
- **预算与止损**：软预算到点先自检，硬预算停止探索并写交接；超预算默认**不中断**，由 Lead 按「追加 / 缩小 / 拆任务 / 换人 / 中断」阶梯决策，详见 `budget.md`。
- 已挂载 `step-budget-guard` 时，硬预算由宿主在 `tools/pre-execute` 强制（被拒调用不执行），成员按 deny 反馈交接即可，不必依赖自觉。

## 信息共享与辩证校验（上游可能是错的）

团队共享上游产物（项目简报、设计文档、前序成员交付），但**上游产物是输入，不是事实**。

| 级别 | 来源 | 用法 |
|---|---|---|
| **L1 事实** | 原始代码/配置、命令输出、官方文档 | 可直接作为依据 |
| **L2 待核** | 上游成员产物（简报、设计、review、test-report） | 引用前必须抽样回溯 L1 |
| **L3 假设** | 成员推断、经验判断 | 必须标注；影响正确性时升级 Lead |

规则：

1. 上游产物每条结论标注 `[已验证]`（附 `文件:行号` 或命令输出）/ `[推断]` / `[待确认]`。
2. 下游引用上游关键结论时，**至少抽样回溯 3 条**到 L1；未核实的不当事实使用。
3. 发现上游与源码/材料冲突：**以 L1 为准**，在交付物中写明冲突（`上游结论 X 与 文件:行号 不符`），并报告 Lead；Lead 决定修订上游产物还是调整任务。
4. **不得静默绕过上游错误**——默默改对会让同一条错误扩散到其他人的交付物。
5. `reviewer` 抽查下游文档对上游的引用是否成立；Lead 终验时核对已知上游错误是否已修订或标注。
6. **Lead 的任务卡描述同样是 L2**：成员发现描述与代码不符时，以代码为准执行并回报，不得默默按错误描述实现；Lead 据此修正任务描述与交付口径。

## 阶段 4：三道质量门（准确交付的核心）

| 门 | 谁 | 通过条件 | 不通过 |
|---|---|---|---|
| G1 自检 | implementer | 改动在 scope 内、目标命令本地通过、无遗留调试代码、写明未验证项 | 自己补齐后再 complete |
| G2 独立复核 | reviewer + tester | review 的 blocking 清零；测试覆盖正常 / 边界 / 失败路径；上游引用已抽查 | `reopen` 返修给原 implementer |
| G3 终验 | Lead | 亲自跑全量命令、diff 范围核对、DoD 逐条勾 | 打回重做，或 Lead 兜底并记录 |

checklist、证据纪律、失败模式见 `delivery.md`。**没有独立复核的改动不得交付。**

## 阶段 5：交付

1. 任务板全部 `completed`。
2. 全量 build / test / lint / typecheck 通过（Lead 亲自跑）。
3. `git diff --stat` 与任务 scope 一致，无越界文件。
4. 上游产物中已知的错误已修订或明确标注；交付物里的 `[推断]` / `[待确认]` 已给出结论或风险说明。
5. 按 `delivery.md` 的模板写交付报告：改了什么 / 为什么 / 怎么验证 / 风险与未覆盖 / 回滚方式。
6. 格式化、锁文件、生成代码收尾统一跑一次。
7. `team-out/` 产物保留作为交付记录，无临时文件残留。

## 异常与升级

| 异常 | 处理 |
|---|---|
| 成员长时间 running 无进度 | 查 `list_agents` status/diagnostics → `interrupt_agent`（保留 inbox）→ 校正方向后 `send_message` |
| 交付不合格 | `reopen` + 返修消息发给原 implementer |
| 返修仍不合格 | `reassign` 给其他成员，或 Lead 接手并记录 ownership 变更 |
| 成员 `failed` | 改名重试或 Lead 接手任务；名字不可复用 |
| 两人结论冲突 | Lead 读代码裁决，禁止成员互相争论 |
| 需要改共享文件 | 成员停下报告 Lead，由 Lead 改或重新切分 |
| 需求变更 | 先改任务描述，再 `send_message` 通知；不可只改消息 |
| 任务/成员指向其它团队 | 停下报告 Lead；跨团队协作只走 Lead↔Lead，不 claim 其它团队任务 |

## 时间与成本

| 阶段 | 正常 | 超出先查 |
|---|---|---|
| 上手简报 | 5–10 分钟（可与编队并行） | 是否在读全仓、逐行读大文件 |
| 创建 2–5 个成员 | < 10 秒 | 是否在等某个成员完成 |
| 实现 | 按改动量 | 任务板 blocked、成员是否在等前置产物 |
| 评审 + 测试 | 2–4 分钟 | 是否忘了 `send_message` 唤醒下游 |
| 终验 | 1–3 分钟 | 命令是否失败、diff 是否越界 |

每名成员至少一轮完整模型调用；`fork` 比 `fresh` 贵。标准阵型典型 4–8 分钟交付。
流水线下游「待命」成员的首轮约 3–6K token；不急着用时可延后到阶段切换再建（见阶段 1）。

## 硬约束（违反即停）

1. 创建期禁止 `wait_agent`。
2. blocked 任务不能 claim/complete；`reassign` 只有 Lead 能做。
3. Git 写操作只有 Lead：成员禁止 commit / checkout / stash / reset / rebase / clean。
4. 运行期 build/test 唯一执行者（默认 tester）；Lead 终验时自己跑。
5. 写作用域文件级、不重叠；重叠就拆任务或串行。
6. 共享文件 Lead 独占，成员不得直接改。
7. 成员不互发消息、不建成员、不建任务、不改任务结构。
8. 无自检不得 `complete`；无独立复核不得交付；证据不能是"应该可以"。
9. 团队 per-session；`inactive` 用 `send_message` 唤醒，不要重建；跨团队不共享任务卡/写作用域，不跨团队派活。
10. 引用上游关键结论必须回溯 L1 原始来源；不得把 L2 当事实。
11. 发现上游错误必须报告并标注，不得静默绕过。
12. 超出硬预算不得静默继续，必须写交接并回报；默认不中断。
13. 同一任务追加预算与返修各不超过 2 次，超过回到拆任务。
